# Decisions

## Proposed project contract (assistant's proposal; no prior project instructions existed)
Written for a test run; may be replaced by the real contract later.
- Layout: monorepo with `backend/` and `frontend/`; CI in `.github/workflows/`.
- Backend: uv, FastAPI, SQLAlchemy 2.x (sync), Alembic, Pydantic v2, pytest, httpx, Ruff, mypy strict on `app/`.
- Frontend: npm, Vite, React, React Router (data router), TanStack Query, openapi-fetch/openapi-typescript, Tailwind v4, Vitest, Testing Library, MSW, Playwright, ESLint with jsx-a11y.
- Accessibility floor: every control labeled, no color-only information, keyboard operable.
- Testing standard and rules of engagement: as stated in the product brief (Backend/Frontend test bullets, Process section).

## Product-owner-confirmed defaults
1. 409 precedence: `game_archived` > `game_finished` > `wrong_board` > `board_already_decided` > `cell_occupied`.
2. GET /games/{id} on an archived game returns 200 with full state; moves return `game_archived`.
3. Location headers: POST /games -> `/api/v1/games/{id}`; POST /games/{id}/moves -> `/api/v1/games/{id}/moves`.
4. "Game number N" is the game's database id.
5. Archiving a finished game is allowed; archiving an archived game returns 409 `already_archived`.
6. Pagination past the end returns 200 with empty `items` and correct `total`; invalid page/page_size return 422.
7. Python pinned to 3.14, `requires-python >=3.13`; if a dependency fails on 3.14, stop and report.

## Deviations and trade-offs from the brief
- GET /games has no `q` param (no named fields to search).
- Status is derived, so the service layer derives status for candidate games, then filters, sorts and paginates; the repository only fetches games with their moves. Cost: O(games x moves) per list call.

## Step 1 choices
- Dependency versions are unpinned (`latest` / no specifier): the sandbox has no network and I won't guess current versions. Lockfiles must be generated by the first install.
- `uv python pin 3.14` could not be run; `.python-version` was written by hand.
- React Router is imported from `react-router` (current package layout); unverified.

## Step 2 choices
- Rule precedence for 409s is implemented once in `validate_move` (see the confirmed defaults above).
- `current_player` stays derived from move count even when the game is over; `active_board` is null when the game is over. Alternative: null `current_player` for finished games. Chosen because the brief lists `current_player` on every list item.
- Replay validates every move (`derive_state` raises a domain error on a corrupt log) instead of trusting stored rows. Cost: replay is O(moves) per read.
- `MovePosition` raises `ValueError` for out-of-range values; the API layer returns 422 before it gets there.
- Domain errors carry a code only; HTTP status mapping belongs to the api/v1 handlers (step 3).
- Database safety nets in addition to service rules: `UNIQUE(game_id, board, cell)` and CHECKs for board/cell in 0..8. Alternative: rely on the service alone. Chosen so a bad write can never persist.
- Constraint naming convention set on `Base.metadata` so migrations are deterministic.
- SQLite foreign keys are enabled per connection in `make_engine`.
- Migration is written by hand (`0001`); a test asserts it matches the models.
- Test helper builds legal full games by playing one board to completion at a time, which is always legal under the literal forced-board rule.

- Ruff treated `alembic` as first-party because `backend/alembic/` exists, and flagged correct import order (I001 x3). Chose `known-third-party = ["alembic"]` over `ruff --fix`, which would have grouped the package with app code. Alternative: rename the migrations folder, rejected because `alembic/` is the conventional layout.
- Added `path_separator = os` to `alembic.ini` to silence Alembic's deprecation warning about `prepend_sys_path` splitting.

## Step 3 choices
- Envelopes: single resources are returned bare; lists use `{items, total, page, page_size}`; errors use `{code, detail}`. 422 also uses the error envelope with code `validation_error`, replacing FastAPI's default shape, so the frontend handles one error type. Alternative: keep FastAPI's default 422 body.
- `GameDetail` adds `is_archived` (not in the brief) because archived games stay readable by direct link.
- `POST /games/{id}/moves` returns the created move plus its derived `player` and `move_number`. Alternative: return the full game state; the frontend refetches the game anyway.
- `GET /games/{id}/moves` takes `page`/`page_size` but defaults `page_size` to 100 (max 100), since a game has at most 81 moves and the default therefore returns all of them. Items include the derived `player` and `move_number`.
- Request bodies reject unknown fields, so a client that sends `player` gets 422.
- Sorting (`created_at`, tie-break `id`) happens in the repository; status filtering and pagination happen in the service, after status is derived. The brief put sorting in the service too; sorting does not need status, so the repository does it and stays testable.
- Layering: repositories flush but never commit; the service commits through `repository.commit()`; one session per request via a FastAPI dependency.
- `create_app(settings)` builds the app; the engine is created in the lifespan. Schema is created only by Alembic (`alembic upgrade head`), never by `create_all` at startup. README (step 6) must say so.
- Removed the unused `CORS_ORIGINS` setting: development uses the Vite proxy and Docker uses the nginx proxy.
- API tests do not run the lifespan; they override `get_session` with a temp-file SQLite database (in-memory SQLite would give each request thread its own empty database).
- `Page[T]` and `_paginate[T]` use Python 3.12+ generic syntax, fine under `requires-python >=3.13`.

## Step 4 choices
- API types come from the backend: `npm run gen:api` runs `app.export_openapi` (dumps `app.openapi()` to `frontend/openapi.json`, no server needed) and then `openapi-typescript` writes `src/api/schema.d.ts`. `schema.d.ts` is committed so CI can typecheck without the backend; `openapi.json` is git-ignored. Alternative: generate from a running server URL, rejected because it needs a live process and a free port. Step 6 CI should regenerate and fail on a diff.
- `VITE_API_BASE_URL` is empty by default (same origin). The OpenAPI paths already include `/api/v1`, so a base URL of `/api/v1` would double the prefix. Tests set it to `http://localhost` because Node's `fetch` rejects relative URLs.
- The client passes `fetch: (request) => globalThis.fetch(request)` so the function is resolved per call. Capturing `fetch` at client creation would bypass MSW, which patches the global later.
- `unwrap()` converts an openapi-fetch result into data or a thrown `ApiError` (status, code, detail), so TanStack Query sees failures as errors; `errorMessage()` produces user-readable text, including for network failures.
- Routes live in `src/routes.tsx` as plain `RouteObject[]` so tests can mount them with `createMemoryRouter`; `main.tsx` uses `createBrowserRouter`. `RouterProvider` is imported from `react-router/dom` (React Router 7 layout); unverified against the installed version.
- Pages are placeholders until step 5. The root layout has a `<main>` landmark; the site name is a paragraph, not a heading, so each page owns the single `<h1>`.
- ESLint uses a flat config as a plain array (no `defineConfig`/`tseslint.config` helper) to avoid depending on which helper the installed version exports. `@eslint/js` was added as a dev dependency because the config imports it.
- ESLint and `@eslint/js` are pinned to `^9`. With `latest`, npm resolved ESLint 10 and `npm install` failed with ERESOLVE because `eslint-plugin-jsx-a11y@6.10.2` only declares support up to ESLint 9. Alternatives: `--legacy-peer-deps` (accepts an unsupported combination, rejected) or dropping jsx-a11y (the accessibility floor wants it). Revisit when the plugin supports ESLint 10.
- Vitest globals are off, so `setup.ts` calls `cleanup()` explicitly after each test.
- Known trap for step 5: passing an `AbortSignal` from TanStack Query into `Request` under jsdom can throw a signal-type error. Step 5 should not forward `signal` to the client unless tests prove it works.

## Step 5 choices
- UI labels use the API's 0-8 indexing ("Board 2, cell 5, empty"), matching the rules in the brief and the backend's error text ("Must play in board 2"). Alternative: 1-9 labels, friendlier but then every backend message would disagree with the screen unless the backend strings were changed too. The status line also names boards by position ("top-right") so numbers are never the only cue.
- "Which boards are playable" is rendered from the server's contract: the game is in progress and not archived, the board is open, and `active_board` is null or equals the board. Cells that already hold a mark are disabled. No win/tie/forced-board logic exists in the frontend.
- List rows: the link reads "Resume game N" or "View game N" (finished games); the Archive button's accessible name is "Archive game N" (visible text "Archive") so each row's button is distinguishable. Alternative: identical "Archive" names, which fail the "every control labeled" intent.
- Page size is a constant 10 so pagination is reachable with few games. Changing a filter or the sort resets to page 1; archiving the last row on a page steps back one page.
- Server state only through TanStack Query: queries use `placeholderData: keepPreviousData` to avoid flicker while paging; moves and archives return the invalidation promise so the mutation stays pending (and cells stay disabled) until fresh state arrives; create does not wait, so navigation is immediate. As specified, queries are invalidated on success only, not on error.
- Query data is shown whenever present, even if a later refetch fails; the error state appears only when there is no data.
- Game page: the status line is a `role="status"` element; move/archive/create errors go into one always-mounted `role="alert"` region so screen readers announce them. Decided boards show a `role="img"` overlay ("Board 0 won by X", large X/O/C). Playable boards use a thick double border plus `data-playable`, never color alone.
- Archived games stay viewable but read-only, and the Archive button is hidden for them. A non-numeric id shows "Invalid game id." and makes no request.
- Test fakes are scripted: fixtures and handlers return fixed states and contain no rules. Default MSW handlers exist for every endpoint (including GET moves, unused by the UI); `moveConflictHandler()` provides the 409.
- Playwright: Chromium only, one smoke test. `playwright.config.ts` starts both servers: the API against a dedicated `data/e2e.db` (migrated with Alembic first) and the Vite dev server (which proxies `/api`). Vitest excludes `e2e/**`.

## Step 6 choices
- Backend image: two stages on `python:3.14-slim`; dependencies come from `uv sync --frozen --no-dev --no-install-project` so the layer caches until `uv.lock` changes; the runtime stage runs as a non-root `app` user (uid 10001) with `/data` owned by it, so the named volume is writable. Startup runs `alembic upgrade head` then uvicorn, because the app never creates tables.
- Frontend image: `node:24-slim` build stage (`npm ci`, `npm run build`), then `nginxinc/nginx-unprivileged` (non-root, port 8080). nginx serves the SPA with an `index.html` fallback and proxies `/api/` to `backend:8000`, so the browser uses one origin and no CORS configuration is needed. `depends_on: service_healthy` matters: nginx fails to start if the `backend` hostname cannot be resolved.
- Healthchecks are defined in `docker-compose.yml` (backend: Python `urllib` against `/health`, since the slim image has no curl; frontend: busybox `wget`). Alternative: `HEALTHCHECK` in the Dockerfiles, which would also cover plain `docker run`.
- The backend port is not published to the host in compose; the API is reached through nginx. Publish `8000:8000` temporarily when debugging.
- Postgres is a commented-out service with the steps needed to use it; the app itself stays SQLite-only.
- CI jobs: backend (ruff, mypy, pytest on Python 3.14 via `backend/.python-version`), frontend (lint, typecheck, test, build), `api-types` (regenerate `schema.d.ts`, fail on a diff), `e2e` (Playwright), `docker` (`compose up --build --wait`, then curl the API and the page). The last two go beyond "lint, typecheck, test" because the brief asks for the smoke test and the containers are otherwise unchecked.
- `.gitattributes` forces LF line endings. Without it a schema file generated on Windows (CRLF) would differ byte-for-byte from the one CI generates on Linux, and `api-types` would fail for no real reason.
- `frontend/scripts/pin-versions.mjs` replaces the `latest` placeholders in `package.json` with `^<installed version>`. It is a one-off helper and can be deleted afterwards. Run it, then `npm install` to refresh `package-lock.json` (otherwise `npm ci` in Docker and CI reports a lockfile mismatch). Python dependencies stay unpinned in `pyproject.toml`; `uv.lock` is the pin, and Docker and CI use `--frozen`.
- Image and action tags are not verified: `ghcr.io/astral-sh/uv:latest`, `astral-sh/setup-uv@v6`, `actions/checkout@v4`, `actions/setup-node@v4`, `node:24-slim`, `nginx-unprivileged:stable-alpine`, `postgres:17` (commented out). Pin the uv image to a version once the first build succeeds.
- Risk: `uvicorn[standard]` pulls `uvloop` on Linux. The lockfile was resolved on Windows, where uvloop is not installed, so Linux wheel availability for Python 3.14 is untested. If the Docker build fails there, switch to plain `uvicorn` in `pyproject.toml` and re-lock.

- First Docker build failed with `"/uv.lock": not found`: the lockfile and the generated `schema.d.ts` were never in the delivered zips (they are produced on the developer's machine), and the project had been extracted into a fresh folder. Not a Dockerfile bug; fixed by copying or regenerating them. Documented in the README. Alternative: have the Dockerfile run `uv lock` itself, rejected because it would make builds non-reproducible.

## Noticed, out of scope
- `GET /games` derives status for every non-archived game on each call: O(games x moves). Fine for a hot-seat app; a stored status would fix it but the brief forbids storing derived data.
- A unique-constraint violation from a concurrent duplicate move surfaces as a 500, not a 409.
- Race: two simultaneous moves to the same game could both pass validation. The unique constraint catches same-cell collisions only; a different cell would land out of turn. Fix would be a stored per-game move number with a unique constraint, but the brief says moves are the only stored gameplay data.
- SQLite returns naive datetimes even for `DateTime(timezone=True)` columns; serialize as UTC in the schema layer (step 3).
